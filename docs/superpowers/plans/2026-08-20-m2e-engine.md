# M2E "Engine" Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task.
> Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace M1's training wheels with the real engine — speed-clock turn
scheduling, flow-field monster chase, seeded five-floor dungeon generation with
stairs and depth-scaled spawns from a five-type bestiary, and tap-to-auto-walk
with interrupts.

**Architecture:** Everything new is a pure function in a new `core` feature file;
`step()` stays the single entry point and grows two thin phases (hero action,
then a scheduled monster phase). Core never learns the bestiary: `GameState`
carries a `FloorBuilder` closure that `content` supplies, so `DescendAction` can
build the next floor from inside `step()` without breaking the dependency rule.
The app's auto-walk is a bloc-owned path plus a self-re-queuing internal event,
so pacing is injectable and every interrupt is a bloc test.

**Tech Stack:** Dart 3.9 (`packages/core`, `packages/content`, pure, `test` +
`equatable`), Flutter 3.47 (`packages/app`, `flutter_bloc`, `bloc_test`). No new
dependencies.

## Global Constraints

- Dependency rule: `app → content → core`. `core` and `content` never import
  Flutter, and never import each other's contents backwards.
- `core` is organised by feature (`dungeon/`, `engine/`), never by kind.
- Game state is immutable; the only mutation channel is
  `(GameState, List<GameEvent>) step(GameState, GameAction)`.
- No global randomness. Every roll draws from an `Rng` carried in state or
  passed in. An unseeded `Random()` in `core` or `content` is a bug.
- No body comments. Dartdoc `///` only, on public API of `core` and `content`.
- Ubiquitous language: the spec's words exactly.
- Accessibility: state and category encoded by shape, marking, position or a
  word — never hue alone. Every screen reads in greyscale.
- Strict TDD in `core` and `content`: red → green → refactor, `// arrange` /
  `// act` / `// assert` bodies, no mocks.
- `app` is tested at bloc level only. No widget or page tests.
- Every commit's exit state is green. Conventional commits,
  `--author="fiatcode <fiatcode@posteo.com>"`.
- Never commit anything under `docs/epic/`.
- Exactly 5 floors; stairs down on 1–4, none on 5. 4-way movement. Fog of war
  radius 8. No loot, skills, town, or death penalty — those are later units.

## Task 2: The speed clock

**Files:**
- Modify: `packages/core/lib/src/engine/energy.dart`
- Test: `packages/core/test/engine/energy_test.dart`

**Interfaces:**
- Produces:
```dart
class TurnSchedule extends Equatable {
  const TurnSchedule({
    required this.monsterTurns,
    required this.heroEnergy,
    required this.monsterEnergies,
  });
  final List<int> monsterTurns;      // indices into the monster list, in act order
  final int heroEnergy;
  final List<int> monsterEnergies;
}

TurnSchedule scheduleMonsterTurns({
  required int heroSpeed,
  required int heroEnergy,
  required List<int> monsterSpeeds,
  required List<int> monsterEnergies,
});
```

**Semantics to document in dartdoc and pin with tests:**
- Every actor gains `speed` energy per tick; an actor at `>= actThreshold` may
  act, spending exactly `actCost`.
- Called after the hero has already acted and spent. Returns the monster turns
  owed before the hero acts again, and everyone's energy once they are spent.
- Hero first on a tie: the loop stops the instant the hero reaches the
  threshold, even when monsters are also at it — they act after the hero's next
  action. **Why:** on a simultaneous threshold the player must never lose agency
  to a coin flip; a monster that "beat" the hero to a shared tick is
  indistinguishable from input lag.
- **Why speed 10 vs 10 must equal M1's alternation:** the whole M1 test suite is
  the characterisation layer for this change. If the clock cannot reproduce
  strict alternation at equal speed, the clock is wrong, not the tests.
- Speeds must be at least 1 — a non-positive hero speed would never reach the
  threshold and the loop would not terminate. Throws `ArgumentError`.

- [ ] **Step 1: Write the failing tests** (all of them, then go green once —
      this is one cohesive unit):

```dart
TurnSchedule scheduleMonsterTurns({...}) {
  _requirePositive(heroSpeed, 'heroSpeed');
  for (final speed in monsterSpeeds) _requirePositive(speed, 'monsterSpeeds');
  final turns = <int>[];
  var hero = heroEnergy;
  final energies = [...monsterEnergies];
  while (hero < actThreshold) {
    final ready = _firstReady(energies);
    if (ready != null) {
      turns.add(ready);
      energies[ready] -= actCost;
      continue;
    }
    hero += heroSpeed;
    for (var i = 0; i < energies.length; i++) energies[i] += monsterSpeeds[i];
  }
  return TurnSchedule(monsterTurns: turns, heroEnergy: hero, monsterEnergies: energies);
}
```

## Task 3: The flow field and the chase rule

**Files:**
- Create: `packages/core/lib/src/dungeon/flow_field.dart`
- Test: `packages/core/test/dungeon/flow_field_test.dart`

**Interfaces:**
- Produces: `Map<Position, int> computeFlowField(FloorMap map, Position goal)`
- Produces: `Position? flowFieldStep(FloorMap map, Map<Position, int> field,
  Position from, Set<Position> occupied)`

**Behaviour arguments for the dartdoc:**
- **Why one shared field rather than per-monster pathfinding:** n monsters cost
  one breadth-first sweep instead of n; every monster reads the same numbers so
  a pack cannot disagree about the route; and because each step must land on a
  *strictly* smaller value, a monster's distance to the hero falls
  monotonically — it can never oscillate between two tiles, which is what a
  greedy per-monster chase does in a corridor.
- **The fixed tie-break order north, east, south, west** makes the choice a
  property of the map, not of iteration order, so a replayed seed replays the
  same chase.
- Unreachable tiles carry no entry; a monster standing on one stands still,
  which is how a walled-off monster stays put.

## Task 6: The floor seed and the generator

**Files:**
- Create: `packages/core/lib/src/dungeon/generator.dart`
- Test: `packages/core/test/dungeon/generator_test.dart`

**Interfaces:**
- Produces:
```dart
int floorSeed(int worldSeed, int depth, int visit);

class GeneratedFloor {
  final FloorMap map;
  final Position heroSpawn;
  final List<Position> monsterSpawns;
  final Position? stairsDown;
}

typedef FloorProblem = String? Function(GeneratedFloor floor, int depth, int monsterCount);

const int maxGenerationAttempts = 8;

GeneratedFloor generateFloor(
  int floorSeed,
  int depth, {
  required int monsterCount,
  FloorProblem findProblem = describeFloorProblem,
});

String? describeFloorProblem(GeneratedFloor floor, int depth, int monsterCount);
```

**Two deliberate deviations from the story spec, argued:**

1. `monsterCount` is a required parameter, not read from a spawn table inside
   the generator. The spec's guarantee list says "monster count from the spawn
   table for that depth", but spawn tables are `content` and the generator is
   `core`; reading the table from inside `core` would invert the dependency
   rule. The count stays a generator guarantee (validated post-hoc), while the
   table that produces it stays content, tested in content.
2. "monster spawns not in the hero's starting room" is enforced by construction
   (spawn tiles are drawn only from rooms other than the hero's) and *validated*
   as the observable consequence: no monster spawn is inside
   `computeFov(map, heroSpawn, fovRadius)`. Rooms are internal geometry and
   putting them on `GeneratedFloor` to satisfy a validator would leak them; the
   field-of-view form is strictly stronger and is what the rule is for — the
   dark has something in it.

**Geometry:**
- Grid `width = 24 + (depth - 1) * 2`, `height = 16 + (depth - 1)` — 24x16 on
  depth 1 up to 32x20 on depth 5, the spec's range exactly.
- Binary space partition: split the longest axis while a rect exceeds
  `maxLeaf` (11x8) and both halves would stay at least `minLeaf` (6); cut point
  drawn from the rng inside the legal band.
- One room per leaf, inset by at least one tile from the leaf border so rooms
  never touch and the grid border stays wall.
- Corridors chain room *i* to room *i+1* in leaf order with an L bend, the
  order of the two legs drawn from the rng. Chaining makes full connectivity
  true by construction; the flood fill is the safety net the game spec's
  section 13 demands, not the mechanism.
- `heroSpawn` = centre of room 0. `stairsDown` = centre of the room whose
  centre is farthest from `heroSpawn` by flow-field distance (ties to the lowest
  index), so the descent is a real walk; `null` on depth 5.
- Monster spawn tiles are drawn from the tiles of rooms other than room 0,
  excluding `stairsDown`.

**Validation, and why bounded retries:** `describeFloorProblem` returns a
diagnostic string or null. `generateFloor` retries with `floorSeed + attempt`
and throws `StateError` with the diagnostic after `maxGenerationAttempts`.
Dartdoc records the argument: the player must never see a broken floor
(game spec 13), and a generator that loops forever on a bad seed is a hang, not
a safety net — so the retry is bounded and the failure is loud.

**The `findProblem` seam:** the default validator does not fail on real seeds,
which would leave the retry contract untestable. The optional parameter is the
seam; its dartdoc says so.

- [ ] **Step 1: Failing tests:**
  - `floorSeed` is stable, differs across depth, visit and world seed, and stays
    inside the 30-bit range `Random` can take on every platform.
  - the same `(seed, depth, count)` returns an identical floor — golden
    `toAscii()` on two seeds, plus spawn positions.
  - a flood fill from `heroSpawn` reaches every walkable tile, depths 1–5.
  - the grid is inside 24x16..32x20 and grows with depth.
  - the border is entirely wall.
  - stairs exist, are walkable and reachable, and differ from `heroSpawn`, on
    depths 1–4; `stairsDown` is null on depth 5.
  - `heroSpawn` is walkable and equals no monster spawn.
  - monster spawns are distinct, walkable, reachable, `monsterCount` of them,
    and none is visible from `heroSpawn`.
  - a validator that rejects the first two attempts returns the floor built
    from `seed + 2`.
  - a validator that rejects everything throws `StateError` carrying the
    diagnostic.
  - a sweep: seeds 0..199 × depths 1..5 all generate without throwing (this is
    what proves the retry bound is adequate, not an assertion of taste).

  final seed = floorSeed(worldSeed, depth, visit);
  final table = spawnTableFor(depth);
  final spawnRng = Rng(seed);
  final count = table.rollCount(spawnRng);
  final generated = generateFloor(seed, depth, monsterCount: count);
  return Floor(
    map: generated.map,
    heroSpawn: generated.heroSpawn,
    stairsDown: generated.stairsDown,
    monsters: [
      for (var i = 0; i < generated.monsterSpawns.length; i++)
        table.rollCreature(spawnRng).spawn(

          at: generated.monsterSpawns[i],
        ),
    ],
  );
}
