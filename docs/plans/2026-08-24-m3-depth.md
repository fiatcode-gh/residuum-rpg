# M3X — randomized depth per delve: implementation plan

> **For agentic workers:** execute inline, task by task, strict red → green →
> refactor. Ledger decision D9 forbids unattended write-capable subagents in
> this epic, so there is no subagent handoff: the mutation table carries the
> adversarial load instead. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A delve's depth becomes part of its roll — the sea-cave lays out four
to six floors and the ruined keep five to seven, uniform, deterministic per
(world, dungeon, visit), recomputed on load, shown in the HUD, with the boss
and the trophy on the rolled bottom and only there. The crypt stays fixed at
five, byte-identical on every path.

**Architecture:** The rolled depth is **derived, never stored**. `delveDepth`
mixes a new purpose slot over `worldSeed ^ dungeonSalt(node)`, so the save
document does not move and `loadRun` recomputes the value exactly as it already
recomputes the floor builder and the drop tables. Core widens by one optional
parameter (`generateFloor` / `FloorProblem` / the validator gain `deepest`,
defaulting to today's `deepestDepth`) and one optional-with-default field
(`GameState.deepest`). Content threads the roll through `dungeonFor` into
`themedFloor`; the app reads it off the view state.

`dart` / `flutter`). Packages: `core` (pure Dart rules), `content`
(declarative data), `app` (Flutter shell). Dependency rule `app → content →
core`.

## Findings that shaped this plan (measured, not assumed)

Run before writing any code, with a standalone Dart probe reproducing
`floorSeed` and `dungeonSalt`:

- **The mix is uniform.** Over visits 1..3000 the three values split
  1001/1000/999, 998/1000/1002, 1000/1000/1000, … for every world seed tried
  (1, 5, 909, 4242, 123456, 1755800000000) and for both dungeons. `mix % 3`
  over the 30-bit FNV hash needs no shaping.
- **Every world reaches every depth quickly.** All three values appear by
  visit 3 (sea-cave, worlds 1 and 4242) and by visit 7 at worst (keep,
  world 1). Over worlds 1..2000, **zero** worlds miss a value across visits
  1..40 — so the variance test is stable at the sweep sizes this suite uses.
- **The pinned characterization visit moves both bottoms.** At the themed
  characterization pin (`_pinnedSeed = 4242`, `_pinnedVisit = 1`) the roll is
  **sea-cave 6** and **keep 7**. Both bottom-floor goldens therefore re-pin, as
  the spec predicted. The two *first*-floor goldens do **not** move: at depth
  one the stairs decision is `1 < deepest`, true for 5, 6 and 7 alike.
- **The survivability bands will move by construction.** At visit 1 over world
  seeds 1..40 the sea-cave rolls `{4: 18, 5: 10, 6: 12}` and the keep rolls
  `{5: 16, 6: 13, 7: 11}`. Eighteen of forty cave delves get *shallower* and
  twenty-four of forty keep delves get *deeper*, so both win counts and both
  histograms are new figures for ratification.

## Shape deviations, pre-declared

Each of these differs from the letter of the spec and is owned here.

- **D1 — `startRun` takes a function, not an int.** The spec says "`startRun`
  gains an optional `deepest` it passes through". A bare `int` forces
  `startDungeonRunAt` to compute `profile.visit + 1` itself in order to name
  the visit the roll is for — a second copy of the visit-bump rule, which
  `startRun`'s own dartdoc says must have exactly one home ("the first one that
  forgot would replay the same five floors forever while looking exactly like
  the ones that did not"). So `startRun` takes
  `typedef DelveDepth = int Function(int visit)` and applies it to the visit it
  bumped. This mirrors the existing `typedef Dungeon = FloorBuilder
  Function(int visit)` exactly, in the same file, for the same reason.
- **D2 — `delveDepth` answers for the crypt instead of throwing.** The spec
  says "the crypt never calls it". `delveDepth(cryptNode, …)` returns
  `deepestDepth` on the first line, before `floorSeed` or `dungeonSalt` is
  touched — the same early-return `dungeonFor` uses for `residuumDungeon`. Both
  callers that need an answer for an arbitrary node (`loadRun`,
  `startDungeonRunAt`) then have one door instead of a crypt branch each.
  Identity by construction is preserved: the crypt still never reaches the mix.
- **D3 — `themedFloor`'s `deepest` is required, not optional.** `dungeonFor` is
  its only production caller. Required forces the characterization test to say
  which bottom it is pinning, and removes the silent-wrong-bottom failure mode
  an optional default would leave behind.
- **D4 — `FloorProblem` gains a required fourth positional parameter.** An
  optional positional would keep the six existing `describeFloorProblem(…)`
  call sites compiling, but would let a custom validator ignore the bottom —
  the exact hole this unit exists to close. Cost: six call updates and two
  lambdas in `packages/core/test/dungeon/generator_test.dart`. Test-only churn.
- **D5 — `ThemedDungeon` carries the band's ends, not a lowest-and-span.**
  Two fields, `shallowestDelve` and `deepestDelve`, inclusive. The range-bounds
  test reads the ends directly; "span" is a derived number nothing else wants,
  and `delveDepth` derives it.
